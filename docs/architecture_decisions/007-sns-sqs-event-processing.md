# ADR-007: SNS + SQS for Asynchronous Video Processing

## Status
Accepted

## Date
08-06-2026

## Context

The platform requires an event-driven workflow capable of processing video
uploads asynchronously. Video transcoding is a long-running operation that
may take several minutes depending on source file size, codec, bitrate,
resolution, and the number of output renditions generated.

The Video Service API must remain responsive to users and should not wait
for transcoding to complete. Upload orchestration, metadata management,
and playback operations must be decoupled from the transcoding pipeline to
prevent a failed or overloaded transcoder from affecting the customer-facing
API layer.

The platform also requires durable message delivery, retry capability, and
the ability to add future consumers (analytics, notifications, moderation,
content indexing) without modifying the upload workflow.

The ingestion workflow begins when a content manager uploads a source file
to the ingest bucket using a pre-signed URL generated by the Video Service.

```text
Content Manager
        │
        ▼

Video Service
        │
        ▼

S3 Ingest Bucket
        │
        ▼

Video Processing Workflow
```

The architectural decision is how the platform should process upload events
after the object arrives in S3.

---

## Alternatives Considered

### Option 1 — Direct ECS Invocation from S3 Event Notification

S3 Event Notifications invoke a Lambda function which immediately launches
an ECS Fargate transcoding task.

```text
S3 Upload
     │
     ▼

Lambda
     │
     ▼

ECS Fargate Worker
```

**Evaluated and rejected for the following reasons:**

- No durable buffering layer exists between upload and transcoding
- If ECS task creation fails, the event may be lost after Lambda retries
- No visibility into backlog size or processing rate
- Difficult to add additional downstream consumers later
- Tight coupling between upload events and transcoding execution

This approach is operationally simple but lacks resilience and scalability.

---

### Option 2 — Lambda-Only Processing

Use Lambda functions to perform all transcoding work directly.

```text
S3 Upload
     │
     ▼

Lambda
     │
     ▼

HLS Output
```

**Evaluated and rejected for the following reasons:**

- Lambda execution duration limits are unsuitable for large video files
- Video transcoding is CPU-intensive and may exceed Lambda memory limits
- Packaging FFmpeg and codec dependencies inside Lambda increases complexity
- Performance becomes unpredictable for large uploads
- Not aligned with the ECS-based compute strategy already adopted by the platform

Lambda remains appropriate for orchestration but not for media processing.

---

### Option 3 — SNS + SQS + ECS Workers ✅ Selected

S3 publishes upload events to SNS. SNS fans out messages to one or more SQS
queues. A lightweight Lambda consumer reads from SQS and launches ECS
Fargate FFmpeg workers via the ECS RunTask API.

```text
S3 Upload
     │
     ▼

SNS Topic
     │
     ▼

SQS Queue
     │
     ▼

Lambda Consumer
     │
     ▼

ECS Fargate Worker
```

**Selected for the following reasons:**

- Durable message storage via SQS
- Natural retry mechanism and Dead Letter Queue support
- Upload events are decoupled from transcoding execution
- SNS fan-out enables future consumers without modifying the upload path
- ECS workers can scale independently of API workloads
- Queue depth provides operational visibility into system load
- Aligns with AWS event-driven architecture best practices

---

## Decision

Use **SNS + SQS** as the asynchronous event backbone for the video
processing pipeline.

### Event Flow

```text
Content Manager Upload
          │
          ▼

S3 Ingest Bucket
          │
          ▼

S3 Event Notification
          │
          ▼

SNS Topic
          │
          ├──────────────► Future Analytics Consumer
          │
          ├──────────────► Future Notification Service
          │
          └──────────────► Video Processing Queue
                                  │
                                  ▼

                            SQS Queue
                                  │
                                  ▼

                           Lambda Consumer
                                  │
                                  ▼

                          ECS RunTask API
                                  │
                                  ▼

                         ECS Fargate Worker
                                  │
                                  ▼

                        S3 Delivery Bucket
                                  │
                                  ▼

                           CloudFront CDN
```

### Queue Design

The transcoding queue is configured with a Dead Letter Queue (DLQ):

| Setting | Value |
|----------|----------|
| Visibility Timeout | Greater than expected Lambda execution |
| Message Retention | 14 days |
| DLQ Enabled | Yes |
| maxReceiveCount | 3 |

Failed messages are automatically moved to the DLQ after three failed
processing attempts.

### Lambda Responsibility

The Lambda function acts solely as an orchestration layer.

Responsibilities:

- Receive SQS messages
- Validate event structure
- Launch ECS Fargate transcoding task
- Record task metadata
- Acknowledge successful processing

The Lambda function does **not**:

- Download video files
- Execute FFmpeg
- Perform transcoding
- Write HLS output

This keeps the orchestration layer lightweight and inexpensive.

### Future Fan-Out Consumers

The SNS topic is intentionally placed ahead of the queue to support future
event consumers without modifying the upload pipeline.

Potential consumers include:

| Consumer | Purpose |
|-----------|---------|
| Analytics Service | Content ingestion metrics |
| Notification Service | Email upload completion alerts |
| Moderation Service | Automated content scanning |
| Search Indexer | Metadata extraction and indexing |
| Audit Pipeline | Compliance and operational logging |

New consumers can subscribe to the SNS topic independently without
impacting the transcoding workflow.

---

## Consequences

- **Positive:** Upload processing is fully asynchronous and does not block
  API requests.
- **Positive:** SQS provides durable message storage and protects against
  transient service failures.
- **Positive:** Dead Letter Queues provide operational visibility into
  failed processing events.
- **Positive:** SNS fan-out enables additional consumers without changing
  the upload workflow.
- **Positive:** ECS transcoding workers can scale independently from the
  API layer and queue depth.
- **Positive:** Queue depth becomes a measurable operational metric for
  monitoring ingestion demand.

- **Accepted trade-off:** Additional AWS services (SNS, SQS, Lambda) increase
  infrastructure complexity compared to direct ECS invocation.
- **Accepted trade-off:** Eventual consistency is introduced into the upload
  workflow — uploaded content may not be immediately available for playback.
- **Accepted trade-off:** Operational troubleshooting requires visibility
  across multiple services rather than a single synchronous execution path.

- **Future:** Evaluate EventBridge Pipes as a replacement for the Lambda
  orchestration layer if operational complexity outweighs the flexibility
  provided by the current design.
- **Future:** Introduce auto-scaling policies driven by SQS queue depth to
  increase transcoding throughput during peak ingestion periods.
- **Future:** Add content moderation and analytics consumers as additional
  SNS subscribers without changing the ingestion workflow.
